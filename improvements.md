# Improvements

- **Direct Circuit Breaker Trip on ConnectError**: In `xml_adapter.py`, when catching `httpx.ConnectError`, we currently call `check_health_and_trip()`. Since a connection error already means the TCP port 8082 is closed, pinging `/health` on that same port is redundant and guaranteed to fail. Calling `xml_circuit_breaker.trip()` directly would fail fast and eliminate an unnecessary network round-trip.

- **Fail Fast on TimeoutException (No Retries)**: In `xml_adapter.py`, the code currently retries `TimeoutException` up to 5 times. Since `XML_TIMEOUT` is 3.0s (which already exceeds the server's known max delay of 2.4s), a timeout indicates the server is severely overloaded, hanging, or frozen. Hammering a busy server with immediate retries will likely just cause 15+ seconds of latency and more timeouts. We should fail immediately on a timeout and let the client back off, rather than aggressively retrying.

- **Move Local Imports to Module-Level (PEP 8)**: In `app/main.py`, several imports (`Resident`, `parse_xml_name`, and `httpx`) are declared locally inside route functions. Moving them to the top of the file aligns with PEP 8 standards, avoids repeated import evaluations during request handling, and makes module dependencies explicit upfront.

- **Remove Dead Code (`last_error`)**: In `xml_adapter.py`, the variable `last_error` is initialized and assigned string values during retries (lines 110-113, 145-148). However, it is never appended to the `warnings` list or used anywhere else. Removing this variable and its assignments will clean up the code.

- **Live Upstream Health Checks for `/status` Endpoint**: In `app/main.py`, the `GET /status` endpoint currently hardcodes the REST service status as `"available"` and only relies on the passive circuit breaker state for the XML service. An important improvement would be to asynchronously ping both upstream `/health` endpoints in real-time during a `/status` request to return a truly accurate, live view of system health.

- **Remove Leftover REST Cache Code**: In `app/cache.py`, the constant `REST_CACHE_TTL = 60.0` (line 19) and the conditional `ttl = REST_CACHE_TTL if key == "rest_residents" else XML_CACHE_TTL` (lines 34 and 70) are leftovers from when both servers were cached. Since REST caching was deliberately removed (data freshness > performance), these should be cleaned up: remove the `REST_CACHE_TTL` constant and replace both conditionals with `ttl = XML_CACHE_TTL`.

- **Remove Unused `fetch_single_benefit()` Function**: The function `fetch_single_benefit()` in `xml_adapter.py` (lines 170–235) is defined and imported in `main.py` (line 11) but never actually called anywhere in the codebase. It was likely written in anticipation of a future per-resident benefit lookup endpoint (e.g., `GET /resident/{id}/benefits`) that was never implemented. Both the function definition and the unused import should be removed to reduce dead code.

- **Remove Defensive XML Fallback Check**: In `xml_adapter.py`, the `_parse_records_xml` function contains a fallback check (`if root.tag == "Record":`) to handle scenarios where the API might return a standalone `<Record>` instead of wrapping it in `<BenefitsRegister>`. Since the upstream government server API is legacy and stable, its response format is guaranteed not to change. This fallback block is dead code and should be removed.

- **Leverage Pydantic Auto-Parsing for Nested Lists**: In `main.py` (lines 102–111), we are manually instantiating `BenefitRecord` objects and appending them to a temporary `matched_xml_data` list before passing it into `UnifiedResident`. Pydantic automatically parses lists of dictionaries into nested models. We can eliminate the manual instantiation and inner `.append()` loop entirely by just passing the raw dictionary list directly to `matched_xml_data=matches[resident_id]`.

- **Remove Redundant `.capitalize()` on XML Names**: In `matcher.py`, the `parse_xml_name()` function converts the all-caps last name into Title Case using `.capitalize()`. However, the parsed name is only ever used in `compare_names()`, which immediately converts both names to `.lower()` anyway for a case-insensitive match. The `.capitalize()` step is completely redundant, wastes CPU cycles, and should be removed.

- **Advanced Fuzzy Matching for "Grey Area" Near-Misses**: Currently, a resident with a matching Name (30), matching City (15), missing DOB (5), and a slight typo in the Address (0) scores a 50 and is completely rejected. When a match score falls into the 50-69 "grey area" (especially when DOB is missing), we should not outright reject the match. Instead, we should either apply an advanced fuzzy-matching algorithm (like Levenshtein distance) to the address/town strings, or flag the record for manual human review by a caseworker.

- **Fix Search Filter Order to Allow Typo Healing**: In the `/residents/search` endpoint, we currently filter the REST residents by the search term *before* running the identity matcher. This creates a structural flaw: if a resident's name has a data-entry typo in the REST system, they are immediately filtered out. Consequently, the identity matcher never gets a chance to evaluate them, preventing it from using its 70% threshold to heal the typo by linking them to a correctly spelled XML record. To fix this, we should run the identity matcher on *all* records first to link them, and then filter the unified results afterward.

- **Improve Search UX for Edge Cases (Typos, Missing Spaces, Extra Words)**: The current search logic in `search_residents` uses exact substring matching (`part in full_name`), which creates rigid failure modes for caseworkers. If they type `"michel"` (typo), it fails because there is no fuzzy string matching (like Levenshtein distance). If they type `"michaelwhitlock"` (missing space), it fails because the code compares it against the artificial space injected between first and last name (`f"{first} {last}"`); stripping spaces from both sides before comparison would solve this. If they type `"michael whitlock kevin"` (extra word), it fails because `all()` requires every word to match. Implementing a more tolerant search algorithm (e.g. fuzzy matching, space-stripping, and partial-word matching) would significantly improve the user experience.
